## 1. Четыре основных справочника

| Таблица | Основные поля | Что хранит |

| Таблица | Основные поля | Назначение |

| `test_competencies` | `test_id`, `competency_id` | Какие способности действительно оцениваются заданием |

| `test_criteria` | `id`, `test_id`, `criterion_id`, `competency_id`, `condition`, `checks`, `assessed_technology_definition`, `scale_code`, `evidence_requirements`, `verification_method`, `critical`, `weight` | Снимок фиксированных проверок и технологической области критерия для версии задания |

Это связи «многие ко многим». Один тест может проверять несколько компетенций, одна компетенция — разными тестами. Компетенция может относиться к нескольким специализациям.

`specialization_competencies` описывает применимость, а не обязательную программу грейда. В ней не должно появляться предположение «обязательно для всех» без соответствующей методики.

Роли технологий различаются: проверяемый инструмент, среда выполнения, вспомогательный инструмент. Использование Docker как среды запуска теста по PHP не подтверждает компетенцию работы с Docker.

Если тест допускает PHP **или** Java, варианты должны быть отмечены как альтернативные группы контекста. Это не требование знать оба языка и не доказательство прохождения на обоих. Параметры альтернатив и совместного применения задаются явно в определении задания.

Опубликованная версия теста не редактируется задним числом; изменение создаёт новую запись версии. Конкретный вариант задания сохраняется в попытке, чтобы результат можно было объяснить позднее.

Справочник из 72 критериев и связи: [ASSESSMENT_CRITERIA_CATALOG.md](ASSESSMENT_CRITERIA_CATALOG.md). Подбор профиля, запрос генератору и формат оценки: [TEST_CRITERIA.md](TEST_CRITERIA.md). Критерии задаёт платформа до генерации задания; ИИ не создаёт шкалу для каждой попытки. `criteria.id` относится к конкретной версии определения; код сохраняется между версиями. `task_profiles.criteria_definition` — черновое определение набора; опубликованные `test_criteria` — его неизменяемый снимок. Физическую нормализацию полей JSON определим при реализации. В `test_criteria` используются компетенции, входящие в `test_competencies` этого теста.

## 2.1. Шаблон задания и поле `selection_conditions`

`task_profiles` — таблица **шаблонов заданий**, не профилей кандидатов. Её название сохраняется для согласованности схемы. `selection_conditions` — **поле JSON внутри этой таблицы**, не отдельная таблица. Его состав теперь определён ниже. База пока не создана; это уточнение проектной модели.

| Поле `task_profiles` | Что хранит |
| --- | --- |
| `id` | ID конкретной версии шаблона |
| `code`, `version` | Постоянное обозначение семейства шаблонов и версия |
| `status` | `draft` — черновик; `published` — проверен и разрешён к выдаче; `archived` — исключён из нового подбора, история сохранена |
| `selection_conditions` | JSON с условиями подбора, структура ниже |
| `assignment_contract` | Что нужно выполнить: входы, результаты, обязательные сценарии, ограничения |
| `criteria_definition` | Выбранные определения критериев, конкретные проверки и правила оценки |
| `generation_policy` | Какие изменения варианта разрешены генератору |

`published` устанавливает ответственный автор после проверки готовности; ИИ не публикует шаблон. Опубликованная версия неизменна. Начальный JSON-профиль пока имеет статус `draft_requires_control_validation`; при импорте это черновик, который не проходит отбор опубликованных шаблонов.

### Источники значений внутри `selection_conditions`

Чтобы JSON-файлы не зависели от ещё не назначенных ID базы, **в условиях хранятся постоянные коды**. В запросе кандидата могут приходить числовые ID; сервер сначала читает соответствующие записи справочников и получает их `code`. Поля с кодами называются `_codes`, не `_ids`.

| Ключ JSON | Тип | Откуда берётся | Как используется |
| --- | --- | --- | --- |
| `specialization_codes` | Массив строк | `specializations.code`, выбранные автором шаблона | Код специализации кандидата должен входить в массив |
| `target_grade_code` | Строка | `grades.code` | Точное совпадение с выбранным предполагаемым грейдом |
| `competency_codes` | Массив уникальных строк | `competencies.code`, выбранные автором | Совпадение множеств компетенций без учёта порядка |
| `competency_match` | Строка | Правило платформы: `exact_set` | Для первого варианта дополнительных компетенций не добавляем |
| `technology_variants` | Массив объектов | Подготовленные автором технологические варианты | Нужно найти один совместимый целиком вариант |
| `technology_variants[].code` | Строка | Постоянный код варианта, задаёт автор | Сохраняется вместе с выданным вариантом задания |
| `technology_variants[].assessed_technology_codes` | Массив уникальных строк | `technologies.code` | Должен точно совпасть с технологиями, которые кандидат выбрал для проверки |
| `technology_variants[].environment_technology_codes` | Массив строк | `technologies.code` | Дополнительная среда запуска; не считается подтверждённым навыком |
| `technology_match` | Строка | Правило платформы: `exact_assessed_set` | Сравниваем технологии проверки, не смешивая их со средой |

Все коды сервер проверяет по справочникам при сохранении / публикации шаблона. В текущем варианте JSON-ссылки не являются внешними ключами базы: целостность проверяет приложение. Если позже выберем нормализованные таблицы связей шаблонов, они заменят эти JSON-связи; обе модели одновременно не ведём как независимые источники.

Условный сокращённый пример для двух компетенций (не запись уже существующей базы):

```json
{
  "specialization_codes": ["backend"],
  "target_grade_code": "middle",
  "competency_codes": ["api-design", "transactions"],
  "competency_match": "exact_set",
  "technology_variants": [
    {
      "code": "php_postgresql",
      "assessed_technology_codes": ["php", "postgresql"],
      "environment_technology_codes": ["docker"]
    }
  ],
  "technology_match": "exact_assessed_set"
}
```

Две записи в `technology_variants` обозначают альтернативы. Например `[PHP, PostgreSQL]` или `[Java, PostgreSQL]` — два отдельных подготовленных варианта. Нельзя собрать непроверенную комбинацию, взяв части разных вариантов. Несколько вариантов допускаются только если контракт и конкретные проверки действительно подготовлены для каждого; иначе создаются разные шаблоны.

### Что приходит от кандидата

Пример запроса (числовые ID условные):

```json
{
  "specialization_id": 1,
  "grade_id": 2,
  "competency_ids": [10, 11],
  "technology_ids": [20, 21]
}
```

В этом примере `specializations.id=1 → code=backend`, `grades.id=2 → code=middle`, `competencies.id=10/11 → api-design/transactions`, `technologies.id=20/21 → php/postgresql`. Это иллюстрация; реальные ID берутся из базы. `technology_ids` здесь обозначает технологии **для проверки**, а среда запуска определяется шаблоном. Проверку существования, активности справочников и применимости компетенций выполняем до подбора.

Нормализованный выбор сервера: Backend / Middle / множество `{api-design, transactions}` / множество `{php, postgresql}`. Он не означает подтверждение квалификации.

## 2.2. Пять шагов подбора: что, откуда и как

| Шаг | Что получаем от кандидата | Что читаем из базы | Условие | Результат |
| --- | --- | --- | --- | --- |
| 1. Готовность | Ничего дополнительно | `task_profiles.status` | `status = published` | Только готовые шаблоны |
| 2. Специализация | `specialization_id → specializations.code` | `task_profiles.selection_conditions.specialization_codes` | Выбранный код входит в массив | Шаблоны для выбранной специализации |
| 3. Грейд | `grade_id → grades.code` | `selection_conditions.target_grade_code` | Коды равны | Шаблоны выбранного контекста сложности |
| 4. Компетенции | `competency_ids → competencies.code` | `selection_conditions.competency_codes` | Множества равны, порядок не важен | Шаблоны, проверяющие ровно выбранные компетенции |
| 5. Технологии | `technology_ids → technologies.code` | `selection_conditions.technology_variants` | Множество выбора равно `assessed_technology_codes` одного целого варианта | Пары «версия шаблона + технологический вариант» |

На каждом шаге проверяем только записи, оставшиеся после предыдущего. Запросы можно объединить в одну операцию; последовательность показывает смысл фильтров. ИИ на этом этапе не используется. Параметры SQL передаются отдельно от текста запроса.

Шаг 1 можно представить независимо от конкретной СУБД:

```sql
SELECT *
FROM task_profiles
WHERE status = :published_status;
```

Дальнейшее чтение JSON зависит от выбранной СУБД. До её выбора не фиксируем конкретный синтаксис JSON-запросов. Эквивалентное правило сервера:

```text
выбор = прочитать и проверить справочники по полученным ID
для каждого шаблона со status=published:
    если specialization_code не входит в условия: пропустить
    если grade_code не совпадает: пропустить
    если множества competency_codes не равны: пропустить
    для каждого технологического варианта:
        если множество assessed_technology_codes равно выбору:
            добавить (template_id, template_version, variant_code) в результат
```

### Пример последовательного исключения

Ниже условные шаблоны для выбора Backend / Middle / API + транзакции / PHP + PostgreSQL. Реальных опубликованных записей в проекте пока нет.

| Условный ID | Статус | Специализация | Грейд | Компетенции | Проверяемые технологии | Что произойдёт |
| --- | --- | --- | --- | --- | --- | --- |
| 41 | `draft` | Backend | Middle | API, транзакции | PHP, PostgreSQL | Исключён на шаге 1 |
| 42 | `published` | Backend | Middle | API, транзакции | PHP, PostgreSQL | Проходит все шаги |
| 43 | `published` | Frontend | Middle | API, транзакции | PHP, PostgreSQL | Исключён на шаге 2 |
| 44 | `published` | Backend | Junior | API, транзакции | PHP, PostgreSQL | Исключён на шаге 3 |
| 45 | `published` | Backend | Middle | API | PHP, PostgreSQL | Исключён на шаге 4 |
| 46 | `published` | Backend | Middle | API, транзакции | Python, PostgreSQL | Исключён на шаге 5 |

Итог примера — шаблон 42 и его вариант `php_postgresql`. Только затем загружаем `assignment_contract`, `criteria_definition` и `generation_policy`, собираем запрос генератору. При выдаче сохраняются использованные версии и конкретный вариант.

Если подходящих шаблонов нет, сообщаем, что подготовленная проверка пока недоступна; не подменяем стек, грейд или набор компетенций. Если есть несколько, предлагаем выбор. Более широкий тест можно предложить отдельно с явным перечислением дополнительных компетенций, но он не считается точным совпадением.

Текущий файл [task-profile-backend-order.json](data/assessment/task-profile-backend-order.json) содержит пять компетенций и статус черновика. Добавлен явный объект `selection_conditions`, согласованный с его верхними полями контекста. Он не подходит под условный выбор только двух компетенций и пока не разрешён к выдаче. Верхние поля JSON являются представлением контекста для генерации; после импорта источником условий подбора служит `selection_conditions`, без независимого редактирования дублирующих значений.

## 3. Правила, связывающие результаты с грейдом

| Таблица | Основные поля | Назначение |
| --- | --- | --- |
| `grade_methods` | `id`, `specialization_id`, `grade_id`, `version`, `scope`, `status`, `validation_reference` | Методика подтверждения конкретного грейда конкретной специализации |
| `grade_method_requirements` | `id`, `method_id`, `competency_id`, `requirement_definition` | Какие доказательства достаточны по отдельной области |
| `requirement_test_criteria` | `requirement_id`, `test_criterion_id` | Какие критерии каких версий тестов допустимы как основания |

Например, отдельная запись методики связывает Backend и Middle. Она определяет достаточность результатов, допустимые варианты, технологическую область и способ совместного применения требований.

Правила и пороги в `requirement_definition` ещё не разработаны. Их нельзя автоматически получить из названий технологий. При реализации формат правил должен быть ограниченным и проверяемым: условия, альтернативы, требуемые результаты и их совместимость.

Условные статусы методики: черновик, проверена / опубликована, архивирована. До публикации валидированной методики грейд не подтверждается. Версия и основания валидации сохраняются.

Сам `test_id` не назначает грейд. Успех одного теста — результат проверки; методика оценивает достаточность всего набора доказательств. Другие результаты и уровни не считаются автоматически пройденными.

## 4. Выбор кандидата и фактические результаты

| Таблица | Основные поля | Назначение |
| --- | --- | --- |
| `candidate_specializations` | `candidate_id`, `specialization_id`, `declared_grade_id` | Выбранные направления и предполагаемые уровни |
| `test_attempts` | `id`, `candidate_id`, `test_id`, `assigned_variant`, `environment_snapshot`, `answer`, `status`, `started_at`, `completed_at` | Конкретная попытка и условия её выполнения |
| `competency_results` | `id`, `attempt_id`, `test_criterion_id`, `result`, `evaluation_details`, `scope` | Что именно подтверждено или не подтверждено по критерию |
| `result_technologies` | `result_id`, `technology_id`, `version`, `role` | Технологии, к которым применим конкретный результат |
| `grade_confirmations` | `id`, `candidate_id`, `method_id`, `scope`, `confirmed_at`, `status`, `next_change_at` | Подтверждённый уровень с методикой и областью |
| `grade_confirmation_evidence` | `confirmation_id`, `result_id` | Результаты, на основании которых подтверждён уровень |

`candidate_id` ссылается на профиль кандидата из общей модели аккаунтов. Заявленный уровень и подтверждения разделены: редактирование заявления не создаёт подтверждение.

Связь технологий хранится на уровне результата, а не только попытки. Это позволяет отличать знания и инструменты, если в одном задании проверяются разные способности на разных частях стека.

Неуспешная попытка сохраняется, но не понижает грейд автоматически. История `grade_confirmations` хранится с основаниями; правила актуальности, смены и частоты необходимо отдельно утвердить.

Для будущей модели следует разделять: активное подтверждение, заменённое новым, утратившее актуальность. Эти статусы не означают автоматическое назначение более низкого уровня.

## 5. Категория

Категория — пара `specialization_id + grade_id`. Для первого этапа её можно вычислять через подтверждения и методики, без отдельной дублирующей таблицы `categories`.

Связь: `grade_confirmations → grade_methods → specializations + grades`.

Если для категорий понадобятся отдельные страницы, порядок, описание и настройки, добавить `categories` с уникальным ограничением на пару специализации и грейда. Принадлежность всё равно выводится из действующих подтверждений; кандидат не назначает её себе вручную.

## 6. Условный пример

1. Выбрано: Backend, предполагаемый Middle.
2. Связь Backend с компетенцией: «работа с транзакциями» применима к этой специализации.
3. Задание: оформить заказ с обработкой заданных ошибок. Компетенции: транзакции и реализация серверной логики. Выбран контекст PHP + PostgreSQL.
4. Попытка сохраняет выданный вариант, среду и решение.
5. Оценка сохраняет отдельные результаты по критериям и их технологическую область.
6. Опубликованная методика Backend Middle проверяет этот и остальные необходимые результаты.
7. Если доказательств достаточно — создаётся подтверждение и категория Backend · Middle. Иначе остаются отдельные результаты без назначения уровня.

Это иллюстрация связей, а не утверждённые критерии Backend Middle. Порогов и достаточного набора в проекте пока нет.

Подтверждение Senior в контексте PHP и отдельный начальный результат Python нельзя объединять в Senior Python. Работодатель проверяет уровень и требуемый стек по связанным доказательствам одной допустимой области оценки.

## 7. Результат для интерфейса

Свободный выбор специализаций и тестов сохраняется. Перед тестом показываются его компетенции, стек и применимость; после — конкретный результат. Прогресс к грейду показывается только для существующей опубликованной методики, без придуманного процента и условной суммы любых тестов.

Для работодателя видны подтверждённая категория, область проверки, стек и основания. Непроверенные заявления отдельно обозначаются. Один кандидат не дублируется в подборке из-за нескольких результатов.

## 8. Границы реализации

Перечень задаёт логическую модель; конкретная СУБД, типы полей, индексы и формат определений будут выбраны при реализации. Задания с вопросами, автоматические проверки кода, экспертные оценки, политика пересдач и ФСП потребуют своих деталей. Таблицы `grade_methods` и требования не заполняются автоматически универсальными критериями.
