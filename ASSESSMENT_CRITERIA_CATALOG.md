Дата: **5 октября 2026 года**. Версия: **draft-2026-10-05**. Это стартовый справочник платформы: **72 критерия для 65 компетенций**, с предложенными связями со всеми 120 специализациями. Он не является утверждённым экзаменом или методикой присвоения грейдов.

## 1. Кому принадлежат критерии

Критерии, шкалы и конкретные проверки задаёт платформа **до генерации задания и до его выдачи**. ИИ получает выбранные записи и составляет вариант задачи в их пределах. Во время оценки ИИ возвращает наблюдения и основания по известным кодам; окончательные баллы рассчитываются платформой по фиксированным правилам. Неизвестный код или новый критерий в ответе не принимается.

Постоянный код обозначает наблюдаемый аспект работы. Компетенция объединяет такие аспекты; технология определяет область результата. Название критерия не является готовым тестом: условия, данные, допуски и ожидаемые результаты нужно зафиксировать в профиле задания.

## 2. Общая шкала `checks_0_2_v1`

Каждый критерий теста имеет непустой список проверок `checks`. У каждой проверки есть постоянный ID, конкретное условие, ожидаемые доказательства и признак `blocking`. Статусы: `passed`, `failed`, `unknown`.

| Балл | Правило платформы |
| --- | --- |
| `null` | Хотя бы одна необходимая проверка не оценена надёжно; результат ожидает проверки. Это не ноль |
| 0 | Все проверки оценены: ни одна не выполнена либо провалена блокирующая проверка |
| 1 | Все проверки оценены: выполнена часть, но не все; все блокирующие проверки выполнены |
| 2 | Все проверки оценены и выполнены |

Сначала проверяется достаточность данных, затем правило баллов. Известные провалы сохраняются и отображаются даже при неполной оценке. Для критерия с одной проверкой частичный балл невозможен. Нельзя округлять ответы ИИ или оценивать «общую убедительность» вместо фактов.

`blocking` влияет на балл конкретного критерия. Критичность критерия для успешности всего теста — отдельное правило профиля; порог прохождения не задан этим справочником. Экспертные проверки требуют заранее описанного списка наблюдаемых условий, допустимых альтернатив и контрольных примеров.

## 3. Каталог

В таблицах указаны **шаблоны проверок**. Слова «заданный» и «оговорённый» при подготовке теста обязательно заменяются конкретными условиями. Незаполненный шаблон нельзя публиковать. Проверки относятся только к условию задачи; не требовать весь список от всех кандидатов.

## 4. Связь со специализацией

В JSON каждая из 120 специализаций имеет `competency_ids` и `criterion_codes`. Это **начальные рекомендации применимости**, а не обязательная программа грейда. Для Backend, Frontend, Full Stack и интеграций связи уточнены отдельно; для остальных использованы группы областей, которые нужно уточнять при создании конкретных тестов. Например группа ИБ не означает, что криптограф обязан проходить все проверки сетевого администратора.

Алгоритм отбора: специализация → применимые компетенции → выбранные компетенции → критерии → совместимый профиль задания и стек. Не назначать все рекомендованные критерии автоматически. Full Stack допускает области frontend и backend, но отдельный backend-тест не подтверждает весь Full Stack.

## 5. Технологии и грейды

Критерий не дублируется для PHP, Java и Python. Профиль фиксирует выбранную технологию, версию, окружение и конкретные проверки. Результат сохраняет эту область, поэтому успешное выполнение на PHP не становится подтверждением Python. Для различных технологий нужны проверенные варианты, а не автоматическая подстановка названия языка.

| Параметр | Влияние на подготовку задания |
| --- | --- |
| Специализация | Выбор применимых областей |
| Компетенции | Выбор того, что проверяем |
| Технологии | Конкретное средство реализации, версия, среда и допустимые варианты |
| Предполагаемый грейд | Выбор заранее подготовленного профиля сложности |
| Критерии | Постоянные аспекты оценки и неизменная шкала |
| Условия задачи | Конкретные сценарии, ограничения, доказательства и ожидаемые результаты |

Предлагаемые ориентиры сложности: Junior — ограниченная задача с явным контрактом; Middle — взаимодействующие сценарии и заданные сбои; Senior — кейс с альтернативами, конфликтующими ограничениями и защитой решения. Это ориентиры подготовки, **не валидированная методика уровней**. Балл 2 означает выполнение данного критерия данного задания, а не Senior. Подтверждение грейда остаётся в `grade_methods`.

## 6. Конкретная привязка: Backend / предполагаемый Middle / PHP + PostgreSQL

Профиль [task-profile-backend-order.json](data/assessment/task-profile-backend-order.json) фиксирует API заказа, допустимый ввод, отклонение ошибок и откат при двух сбоях. Из каталога выбраны пять критериев:

| Код | Компетенция | Проверяемая технология | Проверки |
| --- | --- | --- | --- |
| `functional_correctness` | `program-implementation` | php | При товаре 1 с остатком 10 и quantity=1 создан один заказ, остаток 9; При товаре 1 с остатком 10 и quantity=10 создан один заказ, остаток 0 |
| `data_operations` | `sql-queries` | postgresql | После успешного заказа запись содержит ожидаемые product_id и quantity; Остатки других товаров не изменены |
| `input_validation` | `api-design` | php | Нулевое, отрицательное, дробное quantity и неверный формат product_id отклонены без изменений; Несуществующий положительный product_id отклонён без изменений; Quantity больше остатка отклонено без изменений |
| `transaction_atomicity` | `transactions` | php, postgresql | Инъекция сбоя после записи заказа сохраняет исходное состояние заказов и остатков; Инъекция сбоя после уменьшения остатка до commit сохраняет исходное состояние |
| `test_effectiveness` | `test-automation` | Инструмент тестирования уточняется в попытке | Тесты кандидата воспроизводимо проходят на корректном контрольном решении; Тесты обнаруживают контрольный дефект: quantity=0 допускается; Тесты обнаруживают контрольный дефект: заказ сохраняется при сбое изменения остатка |

Docker — только окружение; его квалификация не подтверждается. Конкурентность и идемпотентность исключены из этого задания, несмотря на наличие соответствующих критериев в справочнике. Добавление их в будущий тест требует новой версии условий и проверок.

Профиль содержит конкретные сценарии, но требует фиксации версий, HTTP-контракта, фикстур, контрольных решений и проверки оценочного механизма перед публикацией. Автоматический грейд выключен.

## 7. Текущий процесс MVP

1. Выбираем специализацию, предполагаемый грейд, компетенции и технологии.
2. По активным связям из `criterion-competencies-mvp.json` формируем полный случайный набор пар без повторов компетенций и критериев.
3. Передаём ИИ выбранные параметры, определения критериев и постоянную шкалу.
4. ИИ генерирует задачу и две конкретные проверки каждого критерия; сайт проверяет структуру и сохраняет снимок до выдачи.
5. После решения используем этот снимок, а не новые критерии; сайт вычисляет баллы из наблюдений.
6. Оценки без независимого подтверждения показываем предварительными, грейд автоматически не назначаем.

Подробности: [TEST_CRITERIA.md](TEST_CRITERIA.md). Готовый профиль заказа из раздела 6 — пример расширенного процесса, не обязательная зависимость текущего MVP.

## 8. Хранение и версии

В MVP критерий связан с компетенциями через `criterion_competencies`; условия задачи и конкретные проверки сохраняются в JSON-снимке `tests.criteria_snapshot`, оценки и история — в `test_attempts.evaluation`. `task_profiles`, `test_criteria` и отдельные таблицы результатов отложены. Подробная будущая схема: [TABLES_AND_RELATIONS_EXTENDED.md](TABLES_AND_RELATIONS_EXTENDED.md).

Файлы JSON — данные для реализации, не уже подключённая база или интерфейс. Выданные условия и оценки сохраняются с версиями и историей. Активность критерия и его связи MVP разрешает экспериментальную генерацию, но не объявляет его откалиброванной программой грейда.
