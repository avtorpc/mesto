# Таблицы и связи: упрощённый MVP тестирования

Дата: **6 октября 2026 года**. Статус: модель и загрузочные файлы SQL/CSV подготовлены; рабочая база и интеграция ИИ пока не подключены. Эта версия заменяет обязательный подбор готовых шаблонов: кандидат задаёт четыре параметра, сайт выбирает случайные неповторяющиеся пары компетенция–критерий, ИИ формирует задачу и конкретные проверки.

**Цепочка:** специализация + предполагаемый грейд + компетенции + технологии → критерии из базы → генерация задачи → проверка структуры → сохранение неизменной задачи и её проверок → решение → предварительная оценка.

## 1. Девять таблиц MVP

| Таблица | Поля | Назначение |
| --- | --- | --- |
| `specializations` | `id`, `code`, `name`, `description`, `direction_code`, `active` | Справочник специализаций |
| `grades` | `id`, `code`, `name`, `sort_order` | Предполагаемые Junior, Middle, Senior; не подтверждение уровня |
| `competencies` | `id`, `code`, `name`, `description`, `active` | Справочник проверяемых способностей |
| `technologies` | `id`, `code`, `name`, `kind`, `active` | Справочник технологического контекста |
| `specialization_competencies` | `specialization_id`, `competency_id`, `relevance_description` | Связь специализации с компетенцией (не с критерием); уникальная пара |
| `criteria` | `id`, `code`, `version`, `name`, `description`, `check_templates`, `active` | Постоянные критерии, без прямого поля компетенции |
| `criterion_competencies` | `criterion_id`, `competency_id`, `active`, `scope_note` | Применимость критерия к компетенции; связь многие ко многим, уникальная пара |
| `tests` | `id`, `candidate_id`, `request_key`, `specialization_id`, `declared_grade_id`, `competency_ids`, `technology_context`, `criteria_snapshot`, `assignment`, `status`, `generation_metadata`, `created_at` | Сгенерированная задача кандидата и неизменный снимок её оценки |
| `test_attempts` | `id`, `candidate_id`, `test_id`, `answer`, `evaluation`, `status`, `started_at`, `submitted_at` | Попытка, решение, оценки и источники |

`candidate_id` обозначает ID внешнего аккаунта. Серверной таблицы аккаунтов в текущем HTML-прототипе пока нет; загрузочная схема использует TEXT и не создаёт фиктивный внешний ключ на аккаунт. Для MVP `tests` принадлежит кандидату, без публичного банка переиспользуемых задач. `test_attempts.candidate_id` должен совпадать с владельцем задачи; в SQL это обеспечено составным внешним ключом `(test_id, candidate_id)`. `request_key` уникален в пределах кандидата. Для текущего MVP одна попытка на задачу; повторное выполнение — новая задача, пересмотр — история оценки.

Внешние ключи: `specialization_competencies` → специализация и компетенция; `criterion_competencies.criterion_id` → версия критерия и `competency_id` → компетенция; `tests.specialization_id` → специализация; `tests.declared_grade_id` → грейд; `test_attempts.test_id` → задача. В `criteria` уникальна пара `(code, version)`; для каждого `code` активна только одна версия критерия. В `criterion_competencies` уникальна пара `(criterion_id, competency_id)`; отдельно могут быть неактивны критерий или связь. `default_for_mvp` больше не используется.

`competency_ids`, `technology_context`, `criteria_snapshot`, `assignment`, `evaluation`, `generation_metadata` — JSON-поля, **не дополнительные таблицы**. Ссылки из JSON на справочники проверяет сервер; поля JSON не получают автоматические внешние ключи. Публикация грейдов и поиск работодателем по подтверждениям потребуют расширенной модели позже.

## 2. Многие ко многим в справочнике, один к одному в конкретной задаче

Критерий может применяться к нескольким компетенциям, а компетенция — иметь несколько критериев. Таблица `criterion_competencies` хранит допустимые связи, а не результаты кандидатов. `scope_note` поясняет, какой аспект компетенции оценивается этой связью.

Пример из начальных данных:

| Компетенция | Допустимые критерии |
| --- | --- |
| `program-implementation` | `functional_correctness` |
| `business-logic` | `business_rules`, `functional_correctness`, `input_validation` |
| `api-design` | `api_contract`, `input_validation` |

В одной задаче **каждая выбранная компетенция получает ровно один критерий, а каждый критерий используется ровно один раз**. Уникальность критерия проверяется по его постоянному `code`, не только ID версии. Другие связи того же критерия не приписывают кандидату результаты по невыбранным компетенциям.

1. Проверить ID справочников и применимость компетенций к специализации.
2. Загрузить все активные связи выбранных компетенций с активными критериями.
3. Найти полный набор неповторяющихся пар случайным поиском с возвратом: перемешать допустимые варианты, попробовать первый, при конфликте вернуться и попробовать другой.
4. Если полный набор невозможен, вернуть `NO_COMPLETE_MATCHING`, не выдавать частичный тест и не дублировать критерий. Сообщить, что для выбранного набора недостаточно разных критериев.
5. Сохранить выбранные пары в `tests.criteria_snapshot` ещё до вызова ИИ. Для уже созданной задачи не разыгрывать пары повторно при повторном запросе, генерации, оценке или пересмотре.

```sql
SELECT cc.competency_id, c.id, c.code, c.version,
       c.name, c.description, c.check_templates, cc.scope_note
FROM criterion_competencies AS cc
JOIN criteria AS c ON c.id = cc.criterion_id
WHERE cc.competency_id IN (:selected_competency_ids)
  AND cc.active = :active_value
  AND c.active = :active_value;
```

Нельзя просто независимо брать случайную строку для каждой компетенции: один критерий может повториться, а жадное исключение повтора может ошибочно отвергнуть допустимый полный набор. Например сначала назначить `functional_correctness` бизнес-логике означает оставить программную реализацию без варианта. Поиск с возвратом назначает бизнес-логике другой критерий и завершает набор.

Случайность означает перемешивание ветвей поиска, **не гарантированную равновероятность всех возможных наборов**. Для MVP с 1–3 компетенциями полный поиск небольшой; это не механизм одинаковой сложности или справедливого ранжирования. Реализация выбора: [criterion-selection.js](js/criterion-selection.js), пока не подключённая к интерфейсу и API.

Справочник: [criteria-mvp.json](data/assessment/criteria-mvp.json); связи: [criterion-competencies-mvp.json](data/assessment/criterion-competencies-mvp.json). При импорте коды и версии разрешаются в реальные ID. Поддерживаем одну активную версию кода; случайный выбор не переключает версии.

Специализация ограничивает применимость компетенций; грейд задаёт ориентир сложности; технологии задают средства работы. На первом этапе выбираем пары по применимости к компетенции, без отдельной технологической матрицы. Генератор может отказать, если выбранная пара и стек не позволяют составить связную задачу; не добавлять другую технологию незаметно. Более точную фильтрацию по стеку можно добавить после пилота.

## 3. Что делает ИИ

На вход получает четыре выбранных параметра, полные определения выбранных критериев и единую шкалу. Готовые шаблоны не нужны.

На выходе: текст задачи, что сдавать, ограничения и **ровно две конкретные наблюдаемые проверки для каждого переданного критерия**. Обе проверки должны быть частью условий, понятных кандидату. Код, версия, компетенция и смысл критерия сохраняются; модель не добавляет критерии и не меняет шкалу.

Генератор формулирует конкретный сценарий и ожидаемый результат, например для `transaction_atomicity`: успешная операция согласованно обновляет данные; сбой между изменениями не оставляет частичной записи. Эти сценарии автоматически сохраняются в `tests.criteria_snapshot` до начала попытки, а не меняются после получения ответа.

Это генерация задания по постоянным критериям, а не поиск готового шаблона. При необходимости сгенерированную задачу можно позднее использовать как основу банка задач.

## 4. JSON-поля задачи

| Поле | Содержимое |
| --- | --- |
| `competency_ids` | ID всех выбранных компетенций; набор проверяет сервер |
| `technology_context` | ID и коды выбранных технологий, роль `assessed` / `environment_only`, версия если задана. Дополнительную технологию модель не назначает обязательной без согласования |
| `criteria_snapshot` | ID, код и версия критерия, ID компетенции, копия описания, `scale_code=mvp_checks_0_2_v1`, две конкретные проверки с локальными ID и ожидаемыми основаниями. ID базы и неизменные поля вставляет сервер |
| `assignment` | Текст, ожидаемый результат, что сдавать, ограничения и явно описанные сценарии |
| `generation_metadata` | Версия инструкции, модель если используется, исходный выбор, ошибки генерации и дата. Параметры формирует сервер, не ответ модели |

Шкала `mvp_checks_0_2_v1` — константа приложения, не отдельная таблица. **0:** обе проверки не выполнены; **1:** выполнена ровно одна; **2:** выполнены обе; **null:** хотя бы одна не оценена по достаточным основаниям. Весов, блокирующих проверок, общей критичности и автоматического порога прохождения в MVP нет. Известный провал сохраняется даже при `null`. Это упрощённая шкала; она отличается от расширенной `checks_0_2_v1` с блокирующими проверками.

## 5. Минимальные серверные шаги

1. Проверить выбор, загрузить связи и сформировать полный случайный набор уникальных пар.
2. Создать `tests` со статусом `generating`, снимком исходного выбора и зафиксированными парами компетенция–критерий. Повтор того же запроса не создаёт лишнюю задачу: используем ключ запроса.
3. Вызвать генератор с ограничением времени. Не передавать имя, контакты и полное резюме.
4. Проверить ответ: точный набор кодов/версий и назначенных компетенций, два непустых условия на критерий, уникальность локальных ID, наличие задания, отсутствие добавленного обязательного стека. Структурная проверка не доказывает содержательную правильность.
5. При некорректном формате повторить запрос максимум один раз с описанием ошибок. При отказе, тайм-ауте или повторном сбое сохранить `generation_failed`; это не результат кандидата.
6. При корректном ответе согласованно сохранить задание и снимок критериев, установить `ready`. В MVP `ready` означает техническую готовность к экспериментальному прохождению, **не экспертную сертификацию задачи**. Дополнительную автоматическую проверку содержательной согласованности другим запросом ИИ можно подключить позже; это не доказательство качества само по себе.
7. При начале создать `test_attempts` со статусом `in_progress`. Не редактировать выданную задачу; для изменений создать новую запись.
8. При отправке сохранить решение, поставить `evaluating`; передать оценщику сохранённую задачу, критерии, ответ и фактические проверки, если они действительно проводились.
9. Проверить наблюдения по каждой сохранённой проверке, рассчитать баллы по константе шкалы, сохранить `evaluation`. Без независимых доказательств выводы имеют статус `preliminary`. Неожиданный код, противоречие проверкам или невозможность оценки → `awaiting_review`; не превращать сбой в ноль.

Генерацию и оценку выполнять на сервере, ключи ИИ в браузер не передавать. Подготовленный код кандидата автоматически не исполняется этим MVP; запуск требует отдельного изолированного механизма. ИИ-анализ кода без запуска — предварительная оценка подхода, а не проверенное выполнение.

## 6. Хранение оценки без дополнительных таблиц

`test_attempts.evaluation` содержит полный ответ оценщика, нормализованные наблюдения `passed/failed/unknown` по ID проверок, рассчитанные баллы по кодам критериев, объяснения, существующие основания, источник и статус `preliminary/awaiting_review/verified`. Значение `verified` может выставить сервер только на основании фактически выполненных независимых проверок / экспертного пересмотра, не заявления ИИ.

История оценки хранится в массиве `revisions` этого JSON-поля; пересмотр не стирает первую оценку. Повторное нажатие отправки не запускает параллельные оценки той же попытки; сохранение результата и смена статуса выполняются согласованно. Конкретное блокирование и индексы определим при реализации.

Сайт показывает выбранную область, конкретную задачу и оценки по критериям. Допустима сумма из `2 × число критериев` с пометкой предварительного результата. Разные автоматически сгенерированные задачи не считаются одинаковыми по сложности: сумму не используем для ранжирования кандидатов и автоматического присвоения Junior / Middle / Senior.

## 7. Что отложено

Для MVP **не нужны** `task_profiles`, `selection_conditions`, `test_competencies`, `test_technologies`, `test_criteria`, `competency_results`, `result_technologies` и таблицы методик грейдов. Их роли в текущем процессе выполняют снимки выбранных уникальных пар и JSON внутри задачи / попытки. `criterion_competencies` теперь включена в MVP; других новых таблиц не добавляем.

Подтверждённые категории и грейды остаются дальнейшей целью ТЗ, но свободная генерация и предварительная оценка её ещё не выполняют. Для этого понадобятся калибровка сложности, проверка качества оценщика и методики достаточности доказательств. Старые подтверждения при будущем запуске не создавать из произвольных сумм MVP.

Расширенная схема и прежний поиск готовых шаблонов сохранены в [TABLES_AND_RELATIONS_EXTENDED.md](TABLES_AND_RELATIONS_EXTENDED.md) как вариант дальнейшего развития. Начальный [профиль заказа](data/assessment/task-profile-backend-order.json) — справочный пример расширенной модели, **не обязательная зависимость MVP**.

Подробные запросы и пример данных: [TEST_CRITERIA.md](TEST_CRITERIA.md), [generation-request-mvp.json](data/assessment/generation-request-mvp.json), [generated-task-mvp.example.json](data/assessment/generated-task-mvp.example.json). Это документация и данные для реализации; интерфейс прототипа не изменён.

## 8. Фиксация и начальная загрузка от 6 октября 2026 года

Основная модель согласована: четыре справочника; специализация связана с компетенциями через `specialization_competencies`; компетенции с критериями — через `criterion_competencies` многие ко многим. Прямой связи специализации с критериями нет. В итоговой задаче случайно выбирается одна уникальная пара на компетенцию без повторения критерия. Грейд и технологии задают контекст задачи, не отдельную матрицу обязательных критериев.

Подготовлены PostgreSQL-схема всех девяти таблиц, seed справочников и связей, CSV для каждой таблицы и отдельный демонстрационный набор задачи / попытки. Инструкция и точные количества: [IMPORT.md](data/assessment/IMPORT.md). Основной набор не содержит вымышленных пользовательских решений или оценок. SQL в рабочую базу пока не загружен.
