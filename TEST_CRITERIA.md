# Критерии и генерация задачи: MVP без готовых шаблонов

Дата: **6 октября 2026 года**. Статус: уточнённый проект процесса и примеры данных, без подключения ИИ / базы. Прежнее требование сначала найти подготовленный профиль отменено для MVP. Четыре выбранных параметра и постоянные критерии достаточны для запроса генератору; содержательные условия задачи создаёт ИИ, а не автор для каждой комбинации.

Схема: [TABLES_AND_RELATIONS.md](TABLES_AND_RELATIONS.md). Исходный каталог: [ASSESSMENT_CRITERIA_CATALOG.md](ASSESSMENT_CRITERIA_CATALOG.md). Упрощённые критерии: [criteria-mvp.json](data/assessment/criteria-mvp.json). Запрос: [generation-request-mvp.json](data/assessment/generation-request-mvp.json). Демонстрационный ответ: [generated-task-mvp.example.json](data/assessment/generated-task-mvp.example.json), составлен для иллюстрации, не получен реальным вызовом внешнего ИИ и не проверен запуском.

## 1. Что задаёт кандидат и сайт

Кандидат выбирает специализацию, предполагаемый грейд, 1–3 компетенции и технологии для проверки. Сайт проверяет значения и применимость компетенций, загружает активные связи из `criterion_competencies` и случайно выбирает полный набор пар: ровно один критерий на каждую компетенцию без повторов кода критерия.

В справочнике 72 критерия и 78 предложенных связей с 65 компетенциями. Поля `competency_id` и `default_for_mvp` удалены из определения критерия. Связи вынесены в [criterion-competencies-mvp.json](data/assessment/criterion-competencies-mvp.json); все активные допустимые связи участвуют в подборе. При импорте коды разрешаются в реальные ID. Активность означает экспериментальную доступность, не калибровку методики.

Например Backend / Middle / API + транзакции / PHP + PostgreSQL:

| Компетенция | Пример выбранного критерия |
| --- | --- |
| `api-design` | `api_contract` — соответствие заданному контракту API |
| `transactions` | `transaction_atomicity` — согласованность успешной операции и отсутствие частичных изменений при сбое |

Сайт передаёт **полное определение**, а не только код. Специализация определяет область, грейд — ориентир сложности, технологии — средства решения, критерии — что оценивать. Грейд не вводит скрытые требования и не подтверждается успешной генерацией.

## 2. Генератор создаёт конкретную задачу

В запрос включаются четыре параметра, выбранные пары, определения критериев, шкала и общие ограничения генерации. Запрос не содержит заранее подготовленного `task_profile` или `selection_conditions`.

Инструкция генератору:

> Создай одну небольшую задачу по переданным специализации, предполагаемому уровню, компетенциям и технологиям. Для каждого выбранного критерия предложи ровно две конкретные наблюдаемые проверки. Сохрани код, версию, смысл критерия и шкалу сайта. Явно отрази все проверяемые требования в условии задачи. Не добавляй критерии и обязательные технологии. Допускай корректные альтернативные решения. Если сочетание несовместимо, верни отказ с объяснением, не подменяй выбор.

Точный пример пакета находится в [generation-request-mvp.json](data/assessment/generation-request-mvp.json). Для сложности достаточно общей инструкции: Junior — ограниченное действие с явными условиями; Middle — взаимодействующие сценарии с ошибками; Senior — задача с альтернативами и обоснованием ограничений. Эти ориентиры не доказывают равноценность задач одного заявленного уровня.

Генератор возвращает JSON:

- `compatible`: получилось ли составить задачу;
- при отказе — `reason`, без подмены выбора;
- при успехе — `required_technology_codes` с точным набором выбранного проверяемого стека, `title`, `assignment` с условием, ожидаемым результатом, ограничениями и тем, что сдавать;
- `criteria_checks`: ровно по одному элементу на каждый выбранный код критерия;
- у каждого элемента — `criterion_code`, `criterion_version` и назначенную `competency_code` и две проверки с `check_id`, `condition`, `expected_evidence`.

Код, версия критерия и назначенная компетенция приходят из сайта; локальные ID и конкретные условия проверок формирует генератор. Числовые ID базы и технологическую область результата определяет сервер. Критерии привязываются к задаче снимком, а не свободным текстом, меняющим смысл после ответа кандидата.

## 3. Проверка и автоматическая выдача

Сервер проверяет структуру JSON, точное совпадение кодов/версий и назначенных компетенций, число и уникальность проверок, непустые условия, наличие задачи и отсутствие добавленного обязательного технологического стека. Проверка состава стека должна опираться на структурированные поля и ограничения ответа; простое наличие слова в тексте не доказывает, что инструмент обязателен. Свободный текст всё равно может содержать неоднозначность: форматная проверка не гарантирует смысловую правильность.

При некорректном формате — один повтор с пояснением ошибки, затем `generation_failed`. При `compatible=false` — сохранить отказ и показать причину. Не зацикливать генерацию и не выставлять оценку кандидату за ошибки модели.

При корректном ответе сохранить задачу со статусом `ready` и неизменный снимок критериев. Для экспериментального MVP не требуется вручную создавать / согласовывать каждую задачу. `ready` означает техническую готовность, а не экспертное подтверждение сложности. Разбор проблемных задач и выборочная проверка качества генерации сохраняются как процесс контроля пилота.

## 4. Пример: сгенерированная задача

Для выбранных API и транзакций ИИ может сформулировать учебный перевод между двумя счетами на PHP и PostgreSQL. В демонстрационном JSON заранее описаны входы, коды ответа, начальные балансы, учебный сбой и исключённые требования.

| Постоянный критерий | Конкретная проверка 1 | Конкретная проверка 2 |
| --- | --- | --- |
| `api_contract` | Допустимый перевод возвращает HTTP 200 и status=ok | Перечисленные неверные запросы возвращают HTTP 400 и status=error без изменения данных |
| `transaction_atomicity` | Успех согласованно меняет оба баланса | Сбой после списания не сохраняет частичные изменения |

Это условия **именно этой задачи**, сохранённые до выполнения. Конкурентность, авторизация и идемпотентность явно не входят в условие. Их нельзя добавить при оценке из-за слова Middle.

## 5. Простая шкала сайта

`mvp_checks_0_2_v1`, ровно две проверки на критерий:

| Балл | Правило |
| --- | --- |
| `null` | Хотя бы одна проверка не имеет достаточных оснований для оценки |
| 0 | Обе проверки оценены и не выполнены |
| 1 | Обе проверки оценены; выполнена ровно одна |
| 2 | Обе проверки оценены и выполнены |

Статусы проверок: `passed`, `failed`, `unknown`. Сначала проверяется полнота оценки; при `unknown` нет итогового числа, но известные провалы показываются. Нет весов, блокирующих правил и универсального порога прохождения. Даже 2 по критерию означает только выполнение условий конкретной задачи.

Шкала является константой приложения. Она **отличается** от расширенной `checks_0_2_v1`: прошлые снимки с другой шкалой не пересчитываются автоматически.

## 6. Оценка решения

Во второй запрос идут сохранённое условие, снимок выбранных критериев с конкретными проверками, решение и фактические результаты независимых проверок, если они есть. Повторный поиск критериев и новая генерация шкалы не выполняются.

Оценщик возвращает наблюдения по каждому сохранённому коду критерия и `check_id`: статус, объяснение и основания. Ответ кандидата — данные, не инструкция выставить баллы. Без доказательств — `unknown`; ИИ не должен выдавать несуществующие логи запуска за основания.

Сервер проверяет точный состав ответа и источники, вычисляет баллы по константе. Пример фрагмента нормализованного результата, в котором score уже добавлен сервером:

```json
{
  "criterion_code": "transaction_atomicity",
  "criterion_version": 1,
  "checks": [
    {"check_id": "balances_success", "status": "passed", "explanation": "Предварительно: в коде выполняются обе операции."},
    {"check_id": "balances_rollback", "status": "failed", "explanation": "Предварительно: нет отката при описанном исключении."}
  ],
  "score": 1,
  "source": "ai_code_review",
  "status": "preliminary"
}
```

Это демонстрация формата, не фактическая оценка решения. ИИ-наблюдения без запуска можно отображать только как предварительную оценку подхода; они не доказывают работоспособность. Недостаточное основание → `unknown`, а не догадка. Если оценщик не уверен или противоречит фактическим данным, результат направляется на пересмотр. Заявление модели о собственной уверенности не меняет статус.

## 7. Что сохраняем

В `tests` — четыре параметра, выбранные случайные пары, задача, неизменный `criteria_snapshot`, версия инструкции и сведения генерации. В `test_attempts` — решение и JSON `evaluation`, содержащий наблюдения, рассчитанные баллы, объяснения, источники, статус и историю пересмотров. Дополнительные таблицы критериев задания и отдельных результатов в MVP не нужны.

Можно показывать предварительную сумму из 4 для примера с двумя критериями. **Нельзя считать её подтверждённым Middle или сравнивать напрямую с другой произвольно сгенерированной задачей.** Уровень сложности и качество оценщика ещё не откалиброваны.

## 8. Оценка варианта

Преимущества: не нужен ручной банк шаблонов для каждой комбинации; сохраняются известные коды и единая шкала; небольшая схема; задача и правила воспроизводимы по сохранённому снимку.

Ограничения: генератор может создать невыполнимые или разные по сложности задачи; формальная проверка этого не исключает; ИИ-оценщик может ошибаться. Поэтому первый MVP проверяет сценарий генерации и предварительной обратной связи, не объявляет объективное подтверждение грейда.

Исследование [Judging LLM-as-a-Judge with MT-Bench and Chatbot Arena](https://arxiv.org/abs/2306.05685) описывает ограничения ИИ-оценки, включая предпочтение многословных и собственных ответов. Оно исследует оценку ответов моделей, не профессиональную аттестацию; нашей системе нужны собственные контрольные решения и проверка качества.

Расширенная схема остаётся возможностью дальнейшего развития в [TABLES_AND_RELATIONS_EXTENDED.md](TABLES_AND_RELATIONS_EXTENDED.md), но не обязательной зависимостью MVP.
