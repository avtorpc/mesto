## 1. Главный вывод

ТЗ требует не единого «Senior на все технологии», а разработки командой механики подтверждения категории и подбора под потребность. Авторы явно требуют учитывать **специализацию, грейд, стек и результаты тестирования**, но не задают готовой шкалы грейдов, заданий, порогов или формулы рейтинга. Эти правила должна предложить и проверить команда.

Рациональный вариант для нашего проекта: **подтверждённый уровень в конкретной специализации + отдельные подтверждения навыков и стека + объяснение соответствия потребности работодателя**. Грейд сохраняется для выполнения ТЗ, но не используется как универсальное доказательство знания любого фреймворка.

Ваш пример показывает, почему одно обозначение Senior недостаточно: большой опыт PHP, Java, SQL, JavaScript и инфраструктуры не подтверждает владение NestJS и Python, хотя может подтверждать полезные общие инженерные навыки. Подтверждение конкретных компетенций нужно получать отдельно; одного перечисления стека и 20 лет стажа недостаточно для назначения уровня.

## 3. Где в задании остаются неоднозначности

- Примеры категорий описывают продолжительность опыта («до года», «с опытом»), но требования одновременно говорят о грейде, подтверждённом тестом. Стаж и квалификация не равнозначны. Рекомендуем хранить их отдельно и уточнить трактовку у экспертов.
- Не определено, насколько широкий объект оценки: роль вообще, конкретная специализация или специализация в конкретном стеке. Это основное решение нашей методики.
- Не сказано, может ли кандидат иметь несколько подтверждённых специализаций. Для full-stack это полезно; в концепции нужно явно описать такое расширение и подтвердить его допустимость у экспертов.
- Не заданы пороги тестов, минимальное покрытие компетенций, правила экспертной оценки и роль опыта в присвоении уровня.
- Участие ФСП должно помогать ранжированию, но формула и сила влияния не заданы. Нельзя считать соревнования доказательством знания всех производственных технологий.
- Опрос по «отрасли» не имеет готового классификатора. Нужно определить, имеется ли в виду отрасль бизнеса или профессиональное направление.

Поэтому по тексту невозможно восстановить единственную методику, которую якобы задумали авторы. Можно восстановить обязательный маршрут и требования к качеству нашей методики.

## 4. Разбор вашего примера

Исходные сведения: full-stack; PHP, Java, SQL, JavaScript, HTML, CSS, Docker, Kubernetes; 20 лет разработки. Это самоописание и основание подобрать проверки, а не уже верифицированный результат. NestJS и Python в перечисленных навыках не заявлены; отсутствие заявления не доказывает отсутствия умения.

| Потребность: NestJS + Python + Docker + Kubernetes | Что видно из исходных сведений | Что должна показать платформа |
| --- | --- | --- |
| Общая backend-инженерия | Есть опыт PHP, Java и SQL; глубина требует проверки | Результаты проверки API, данных, тестирования и архитектурных решений |
| NestJS | Заявлен JavaScript, но не подтверждено владение NestJS | «NestJS: не проверено»; отдельное задание при необходимости. Java не является JavaScript |
| Python | Навык не указан | «Python: не заявлено / не проверено», без автоматического вывода о некомпетентности |
| Docker | Заявлен | Результат практической проверки, область и дата |
| Kubernetes | Заявлен | Отдельное подтверждение сценариев эксплуатации / диагностики, без автоматического присвоения DevOps-грейда |
| Способность освоить новый стек | Возможны переносимые знания | Основания предположения и подход к новой задаче; срок обучения нельзя достоверно вычислить по стажу |

**Если работодателю нужен специалист, сразу работающий в NestJS и Python:** общий Senior не закрывает эти обязательные условия. При отсутствии подтверждений кандидат попадает в отдельную подборку «требует проверки», если работодатель её разрешил, либо не входит в основную подтверждённую подборку.

**Если работодатель допускает освоение технологий:** подтверждённая backend-инженерия и инфраструктурные навыки могут быть релевантны. Выдача должна сообщить совпадения, пробелы и основания рекомендации, а не просто поставить кандидата выше из-за 20 лет стажа.

Пример будущей карточки, только после получения соответствующих результатов:

> Backend · уровень Senior подтверждён по методике платформы. Проверенный стек: PHP / Java / SQL. Docker: подтверждён. Kubernetes: подтверждён. NestJS / Python: не проверены. Для текущего запроса требуется дополнительная проверка двух технологий.

Это пример отображения, а не оценка вашего фактического уровня.

## 5. Варианты реализации

| Вариант | Как назначается уровень | Польза | Ограничения и соответствие |
| --- | --- | --- | --- |
| A. Грейд по специализации | Один тест для Backend / Frontend / QA и выбранного уровня; стек используется отдельным фильтром | Проще реализовать основной обязательный маршрут | Соответствует базовой связке категории, но мало помогает на стыке технологий; нельзя обещать владение всем стеком |
| B. Уровень по специализации и технологическому направлению | Общие компетенции + модуль выбранного стека, например Backend → PHP или Java | Более точное подтверждение, можно иметь разные результаты по направлениям | Больше заданий и риск слишком мелких категорий; для MVP ограничить направления. Основную категорию сохранить как «специализация + грейд», стек показывать отдельно |
| C. Грейд по специализации + карта компетенций + подбор под запрос | Общий модуль подтверждает заявленный уровень; практические модули подтверждают навыки; соответствие вычисляется под потребность | Сохраняет грейд из ТЗ и показывает работодателю реальные основания выбора | Требует правил минимального покрытия для грейда, отдельных статусов навыков и объяснимого ранжирования; рекомендуемый вариант |

Полная замена грейда одной картой навыков концептуально возможна, но не отвечает буквальному требованию обязательного выбора и тестирования на грейд. Для конкурсного решения такой вариант потребует согласования с организаторами.

Для MVP варианта C достаточно двух специализаций, например backend и frontend, и ограниченного набора уровней, технологий и заданий. Это предложение по объёму, а не установленный ТЗ минимальный список.

## 6. Предлагаемая модель оценки

### 6.1. Подтверждать только то, что проверялось

Для каждой специализации описать уровни через наблюдаемые действия: сложность задачи, самостоятельность, корректность решения, работа с ограничениями, качество тестов и обоснование выбора. Высокая оценка в одном навыке не должна компенсировать провал обязательного навыка для грейда.

Тест может подтвердить уровень по методике платформы в заданном диапазоне задач. Он не доказывает автоматически многолетнюю работу в промышленной команде, наставничество или успешность в любой компании. Такие утверждения требуют своих подтверждений.

В профиле разделить:

- заявленные навыки и опыт;
- выбранный предполагаемый грейд;
- подтверждённую специализацию и уровень;
- результаты по отдельным компетенциям, включая стек;
- статус «не проверено», «проверено на таком-то уровне», «не подтверждено этой попыткой»;
- доказательства, дату, версию методики и область проверки;
- достижения ФСП и статус их подтверждения.

Не назначать низкий уровень только из-за отсутствия проверки технологии. Не распространять результат теста PHP на Python или NestJS.

### 6.2. Тестирование с сопоставимыми вариантами

Предлагаемый подход: **семейства заданий с проверяемыми вариантами**.

1. Эксперты описывают проверяемые компетенции, целевую сложность и критерии оценки.
2. Для каждого уровня задаётся план теста: обязательные темы, практические задания и их доля.
3. Система формирует вариант из проверенных шаблонов: меняются входные данные, ограничения, схема данных и дефекты; набор компетенций сохраняется.
4. Корректность проверяется скрытыми тестами, качество решения и объяснение — по явной шкале, для сложных случаев с экспертной проверкой.
5. Варианты сравниваются на контрольных участниках; слишком лёгкие / сложные варианты исключаются или корректируются.
6. Результат сохраняет не только баллы, но и покрытие навыков, дату и версию.

Описания нескольких потребностей работодателей преобразуются в набор проверяемых компетенций и выбор модулей из банка. Это показывает формирование теста на основе потребности, не требуя неконтролируемой генерации совершенно новых экзаменов.

Параметризация сама по себе не гарантирует одинаковую сложность и не исключает утечки. Нужны ротация семейств, ограничение раскрытия банка и проверка эквивалентности вариантов. Нейросеть можно использовать для черновиков заданий и объяснений, но не считать её неподтверждённую оценку единственным основанием грейда.

Исполнение кода кандидатов, если такой формат выбран, требует изолированного окружения с ограничениями ресурсов. Для первого MVP можно использовать разбор кода, SQL-задачи, диагностику и задачи с заранее определёнными результатами, уменьшив объём исполнительной инфраструктуры.

### 6.3. Не смешивать два ранжирования

**Рейтинг внутри категории:** результаты обязательных проверок и подтверждённые достижения ФСП. Влияние ФСП должно быть ограниченным и объяснимым; отсутствие истории не исключает кандидата и не отменяет успешно пройденные тесты.

**Соответствие запросу:** сначала обязательные условия, затем совпадения подтверждённых компетенций, разрешённые работодателем пробелы, формат и зарплатные ожидания. После этого можно использовать категорийный рейтинг как дополнительный фактор.

Жёсткое условие «подтверждённый Python обязателен» не должно компенсироваться баллами за SQL или соревнования. Если работодатель допускает обучение, это отдельный явный режим подбора. Числовые веса и пороги нужно калибровать на контрольных примерах; нельзя выдавать произвольный процент совпадения за вероятность успешного найма.

### 6.4. Изменение грейда

При неуспешном прохождении не понижать уровень автоматически. Показать результаты и возможность теста на другой уровень по согласованным правилам. При сильном результате предложить проверку следующего уровня. История сохраняется; частота именно смены грейда ограничивается выбранным командой интервалом. Следует отдельно определить правила повторных попыток, первичного подтверждения и обновления отдельных навыков — ТЗ не приравнивает их автоматически к смене грейда.

| Чаты | Общая история, сообщения, статусы, оценка задания | Основная сущность сейчас — отклик. Нужен разговор между участниками, допускающий контекст предложения |

| Приватность | Демо-переключатель видимости резюме | Настройки публикации и согласия, серверные права доступа, раскрытие контактов только при допустимом событии |

| Проверка решения | Проверки логики текущих форм и чатов | Оценка качества тестирования и подбора на собственных контрольных данных, результаты, методика |
| Сервис и сдача | HTML/CSS/JS, Markdown-документация | Backend и общее хранение, API и OpenAPI, воспроизводимый запуск, презентация, сопроводительный документ doc / PDF |

Показ email в текущем чате отклика сам по себе не противоречит ТЗ: кандидат уже откликнулся. Однако для нового предложения работодателя до принятия приглашения те же компоненты не должны раскрывать email.

## 8. Как развивать имеющиеся страницы

1. **Регистрация / кабинет соискателя:** добавить мастер «отрасль → специализация → предполагаемый грейд → тест → результат». Резюме можно заполнять отдельно; оно не должно менять подтверждённые результаты.
2. **Вкладка «Работники»:** сделать вход через категории и подбор под потребность. Карточка содержит уровень, подтверждённый стек, достижения и краткое объяснение; стаж показывается отдельно.
3. **Страница кандидата:** сохранить краткое описание опыта и проекты, добавить подтверждения; вместо несохраняемого приглашения — «Предложить работу» с компанией, описанием, зарплатой от–до и способом связи работодателя.
4. **Кабинет работодателя:** основной раздел «Потребности и кандидаты», затем исходящие предложения. «Мои вакансии» и входящие отклики остаются дополнительными.
5. **Кабинет соискателя:** раздел «Предложения работодателей» с просмотром условий, принятием / отказом и перепиской. Не считать статус существующего отклика заменой входящего предложения.
6. **Чаты:** переиспользовать внешний вид и отправку сообщений, но расширить модель до `conversation` с участниками и источником: `offer` или `application`. Предложение не обязано иметь `vacancyId`.
7. **Сервер:** перевести аккаунты, результаты, категории, предложения и права доступа из браузерного хранилища в общий backend. Для MVP достаточно понятного модульного монолита; микросервисы, ML и Keycloak не являются обязательным выбором технологий по ТЗ.

Предлагаемые сущности: Account, CandidateProfile, Specialization, GradeDefinition, AssessmentAttempt, CompetencyEvidence, CategoryMembership, FspAchievement, EmployerNeed, Offer, Conversation. Существующие Vacancy и Application сохраняются как дополнительный контекст.

## 9. Приоритеты с учётом оценки конкурса

В ТЗ: новая механика подбора — **35%**, тестирование / валидация / категоризация — **25%**. Вместе это **60%** критериев. Классические вакансии, отклики и другие дополнительные функции относятся к отдельному критерию **7%**, причём эти 7% распределены между несколькими возможностями, а не гарантированы только за вакансии.

Предлагаемая последовательность работ:

1. Утвердить узкий объём справочников, правила подтверждения и сценарий предложения работодателя.
2. Сделать сквозной обратный маршрут на тестовых данных, включая предложение с зарплатой и ответ без отклика.
3. Реализовать обязательные сопоставимые тесты и категоризацию, затем объяснимый подбор.
4. Обеспечить общую серверную модель, email обеих ролей и правила видимости; это часть рабочего сквозного сценария, а не отложенная косметика.
5. Добавить тестовую интеграцию ФСП и корректный сценарий без ФСП.
6. Провести валидацию и подготовить результаты, API, инструкцию запуска и материалы сдачи.

Очередную доработку оформления обычных вакансий целесообразно отложить: полезная часть уже есть, но она не закрывает смысловой центр ТЗ.

## 10. Как проверить предлагаемое решение

Данные организаторы не предоставляют. Можно использовать собственные синтетические профили и потребности с заранее зафиксированными экспертными оценками. Малый демонстрационный набор не доказывает качество на всём рынке.

Обязательные контрольные примеры:

- PHP / Java backend с большим опытом против потребности NestJS / Python: общий грейд не перекрывает неподтверждённый обязательный стек.
- Кандидат с меньшим стажем, но подтверждённым нужным стеком: может быть выше для соответствующей потребности.
- Сильный специалист без истории ФСП: доступен в категории; отсутствие истории обозначено корректно.
- Кандидат с достижениями ФСП, но без обязательной технологии: бонус не обходит обязательное условие.
- Разные результаты по backend и frontend: независимые области подтверждения; не распространять уровень одной на другую.
- Непройденный тест: нет автоматического понижения; понятен следующий разрешённый шаг.
- Предложение без вакансии и без отклика: получено кандидатом, имеет зарплату и статус, создаёт диалог.
- Контакты до и после принятия: скрыты / раскрыты согласно правилу; то же проверяется в API.

Метрики: доля релевантных кандидатов в первых позициях (например, Precision@5); частота нарушения обязательных условий; совпадение уровня с экспертной оценкой; стабильность сопоставимых вариантов; различение контрольных уровней; успешность сквозного пользовательского сценария. Для расчёта нужны проверенные контрольные метки, заранее заданные критерии и отчёт о фактических результатах. В этом анализе числовые результаты таких проверок не заявляются.
