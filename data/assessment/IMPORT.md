# Загрузка таблиц MVP

Дата: **6 октября 2026 года**. Формат SQL: **PostgreSQL**, отдельная схема `mesto_assessment`. Также подготовлены CSV в UTF-8. Это файлы для загрузки; рабочая база сайта пока не создана и импорт в неё не выполнен.

## Состав

| Таблица | Основная загрузка | Дополнительный пример |
| --- | ---: | ---: |
| `specializations` | 120 | — |
| `grades` | 3 | — |
| `competencies` | 65 | — |
| `technologies` | 62 | — |
| `specialization_competencies` | 1543 | — |
| `criteria` | 72 | — |
| `criterion_competencies` | 78 | — |
| `tests` | 0 | 1 |
| `test_attempts` | 0 | 1 |

Основной набор создаёт все девять таблиц и заполняет семь справочных / связующих таблиц. Задачи и попытки обычно создаются сайтом, поэтому базовые CSV для них содержат только заголовки. Отдельный демонстрационный набор позволяет увидеть данные во всех девяти таблицах. Он содержит синтетический идентификатор кандидата, авторский пример задачи и неизвестные оценки (`null`), без настоящего решения и без вызова ИИ.

## Вариант 1. Загрузка SQL

Из корня проекта, в существующую базу PostgreSQL `mesto` (имя примерное):

```sh
psql -d mesto -v ON_ERROR_STOP=1 -f data/assessment/sql/01_schema.sql
psql -d mesto -v ON_ERROR_STOP=1 -f data/assessment/sql/02_seed.sql
psql -d mesto -v ON_ERROR_STOP=1 -f data/assessment/sql/04_validate.sql
```

`01_schema.sql` выполняется один раз в новой схеме. Таблицы не удаляет, существующую несовместимую схему не мигрирует: при повторном создании выдаст ошибку и откатит транзакцию. `02_seed.sql` сохраняет уже существующие записи с теми же кодами / версиями и пары связей; без незаметного изменения критериев. Это начальная загрузка, не инструмент синхронизации изменённых справочников.

При необходимости наполнить задачи и попытки примером:

```sh
psql -d mesto -v ON_ERROR_STOP=1 -f data/assessment/sql/03_demo.sql
psql -d mesto -v ON_ERROR_STOP=1 -f data/assessment/sql/04_validate.sql
```

Демонстрационная задача имеет фиксированный `request_key=demo-api-transactions-v1`. Повтор её загрузки не создаёт новую задачу или попытку. SQL разрешает ссылки по постоянным кодам, поэтому демонстрация использует фактические ID загруженной базы.

## Вариант 2. Загрузка CSV

Это альтернатива `02_seed.sql`, не дополнительная загрузка тех же строк. В новой пустой схеме после выполнения `01_schema.sql`:

```sh
psql -d mesto -v ON_ERROR_STOP=1 -f data/assessment/sql/05_import_csv.psql
```

При желании загрузить демозаписи в пока пустые `tests` и `test_attempts`:

```sh
psql -d mesto -v ON_ERROR_STOP=1 -f data/assessment/sql/06_import_demo_csv.psql
psql -d mesto -v ON_ERROR_STOP=1 -f data/assessment/sql/04_validate.sql
```

Файлы `.psql` — сценарии клиента `psql` с командой `\copy`, не обычный SQL для произвольной панели запросов. Запускаются из корня проекта: пути CSV относительные. CSV использует запятую, первую строку с названиями столбцов, стандартное экранирование кавычек и JSON внутри соответствующих полей. Импорт идёт в порядке зависимостей и в транзакции.

Числовые ID в CSV относятся к этому начальному набору. Поэтому CSV рекомендуется для пустой схемы. Для добавления в уже наполненную схему предпочтительнее SQL; при конфликте фиксированного ID с другим кодом загрузка остановится, не перезапишет чужую запись. После вставки начальных ID сценарии обновляют последовательности.

## Установленные связи

- `specialization_competencies.specialization_id` → `specializations.id`.
- `specialization_competencies.competency_id` → `competencies.id`.
- `criterion_competencies.criterion_id` → `criteria.id`.
- `criterion_competencies.competency_id` → `competencies.id`.
- `tests.specialization_id` → `specializations.id`.
- `tests.declared_grade_id` → `grades.id`.
- `(test_attempts.test_id, test_attempts.candidate_id)` → `(tests.id, tests.candidate_id)`.

Пары связей уникальны. У каждого кода критерия разрешена только одна активная версия. Внешние ключи запрещают потерянные ссылки и попытку другого владельца. `request_key` предотвращает повторное создание задачи для одного запроса кандидата. В MVP одна попытка на задачу; повторная самостоятельная проверка создаёт новую задачу, пересмотр сохраняется в истории оценки.

`candidate_id` имеет тип `TEXT` и обозначает ID внешнего аккаунта. В существующем HTML-прототипе нет серверной таблицы аккаунтов, поэтому экспорт не придумывает её и не создаёт фиктивный внешний ключ. При подключении авторизации поле будет связано с реальной моделью аккаунтов. Согласованность владельца задачи и попытки уже обеспечена составным внешним ключом.

Ссылки внутри JSON (`competency_ids`, технологии и снимки критериев) проверяет сервер приложения; обычные внешние ключи на элементы JSON не установлены. `04_validate.sql` дополнительно проверяет сохранённые пары снимка, отсутствие повторов и покрытие компетенций критериями. Проверки содержательной правильности и равноценной сложности задач не заменяются ограничениями базы.

## Источники и принятые правила

Специализации — [IT_SPECIALIZATIONS.md](../../IT_SPECIALIZATIONS.md); компетенции и список технологий — [IT_COMPETENCIES.md](../../IT_COMPETENCIES.md). Отдельное представление технологий: [IT_TECHNOLOGIES.md](../../IT_TECHNOLOGIES.md). Грейды: Junior / Middle / Senior.

Критерии — [criteria-mvp.json](criteria-mvp.json), связи критериев — [criterion-competencies-mvp.json](criterion-competencies-mvp.json). Связи специализаций и компетенций взяты из `specialization_links` файла [criteria-catalog.json](criteria-catalog.json). Это предложенная применимость: часть связей составлена по направлениям и нуждается в уточнении при пилоте, не обязательная программа для всех специалистов.

Модель связей одна: **специализация → компетенция → критерий**. Прямой таблицы «специализация — критерий» нет. Из многих допустимых связей сайт выбирает случайный полный набор неповторяющихся пар; выбранные пары фиксируются в задаче до обращения к ИИ. Ни seed, ни импорт автоматически не присваивают грейды.

## Повторная сборка и проверка

Из корня проекта:

```sh
python3 scripts/generate-assessment-seed.py
python3 scripts/validate-assessment-seed.py
```

Генератор пересоздаёт экспортные SQL/CSV из согласованных документов и JSON; в базу не подключается. Файл [seed-manifest.json](seed-manifest.json) содержит ожидаемые количества и SHA-256 экспортов. CSV следует редактировать через исходные справочники и повторную сборку, иначе SQL и CSV разойдутся.

Проверено: количество и уникальность записей, ссылки всех связей, покрытие всех 65 компетенций, JSON демонстрации и совпадение владельцев. Для проверки ссылочных ограничений использована отдельная модель SQLite в памяти, в том числе ошибочные ссылки и повторяющиеся пары. **PostgreSQL-сервер в этой сессии не запускался; DDL и импорт SQL в PostgreSQL ещё не выполнены.** Для фактической проверки после загрузки используется `04_validate.sql`.

Типы JSONB и ограничения сверены с первичной документацией PostgreSQL: [JSON types](https://www.postgresql.org/docs/current/datatype-json.html), [Constraints](https://www.postgresql.org/docs/current/ddl-constraints.html).
